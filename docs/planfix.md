# Numerical fixes implementation guide

Use `404f1215` as the review baseline. It includes the allocation-free FMA expansion and the corrected cube-root return type. Use `55cc3be3` for the old vector-based FMA comparison and `5f83e5eb` for exponential timings before the optimization series. The logarithm exponent wrap and exponential midpoint error predate that series. The guaranteed-underflow slowdown was introduced by it. Keep the fused polynomial kernels, public method signatures, unrelated dispatch, and arithmetic changes outside the reviewed paths.

## 1. Fix logarithm mantissa scaling

In [explog.jl](../src/math/elementary/explog.jl), keep the near-one path and the existing tiny-input rescale. Fix the low-limb normalization in the table path of `_unsafe_log2`, after the rescale and after computing `er = _raw_exponent(hi)`. The scale is `2^-er` and the normalized leading limb is in `[1, 2)` for positive finite inputs.

1. Read the low limb's exponent field with the existing helper. Admit a nonzero low limb to `_uldexp` only when its source exponent field is normal and its destination exponent, `_raw_exponent(lo) - er`, is in the finite normal range. Both endpoints of that range are inclusive. Compare signed exponents before doing any unsigned bit arithmetic.
2. Select zero for an out-of-range low limb before passing it to `_uldexp`, which already handles zero. For a normalized input pair, overflow of the destination low limb is impossible. A subnormal destination is smaller than the working precision of a mantissa near one, so discarding it is safe on this path. A source subnormal that matters is made normal by the existing tiny-input rescale. The direct near-one path stays ahead of this check because tiny corrections can matter when the log itself is near zero.
3. Keep the check at the log call site. Document the source and destination requirements on `_uldexp` and retain the existing handling for log domain errors, zero, infinities, and NaN.

## 2. Restore the early underflow return

In `_exp2_clamped`, return the zero tuple before reduction, polynomial evaluation, and integer conversion when the leading base-2 exponent is below the existing conservative `_exp2_zero(T)` cutoff. The cutoff has five exponent units of margin below the zero midpoint. That covers the trailing limbs for normalized finite inputs of both precisions. Keep the margin and use an ordered comparison so NaN bypasses the zero return. Verify that `-Inf` takes the zero path for all three entry points and that `+Inf` and NaN retain their public behavior.

Keep one copy of the range reduction and polynomial evaluation per call. Compare the early-return implementation against both reference revisions before changing branch layout further.

## 3. Round subnormal exponentials from the full approximation

Let `emin` be the minimum normal exponent, `p` the precision including the implicit bit, and `q = nextfloat(zero(T)) = 2^(emin - (p-1))`. The values in the subnormal range and at the minimum-normal boundary lie on a lattice with spacing `q`. Use both limbs to select a lattice point before either limb is scaled into underflow.

1. Factor the end of `_exp2_kernel` so the shared reduction returns the two limbs `(ph, pl)` of the reduced exponential and the integer reconstruction exponent `n`. Keep the existing split scaling for ordinary results. Route the low band through dedicated reconstruction when the leading converted exponent is at or below `_exp2_min(T)`, including equality because the trailing limbs can put the exact argument on either side. Verify the dispatch bound for converted arguments as well as for direct `exp2`. At equality the lattice also covers the small overlap above `floatmin(T)` in the first normal binade.
2. In the low band, multiply both reduced limbs by `2^(n - (emin - (p-1)))` to express the result in units of `q`. With the current cutoffs the scaling exponent ranges from `-6` through `p-1`. Keep the scaled limbs separate. Pick a candidate integer from the high limb, then compare the signed residual formed from both limbs against the adjacent half-integer boundaries. Use ties-to-even and verify the residual comparison against exact arithmetic for both signs of the low limb. The IEEE encoding of each nonnegative output through the first normal binade is its lattice index. Construct the high limb directly from that index to avoid a subnormal multiplication, and return a zero low limb.
3. Resolve the exact zero midpoint for direct `exp2` from the input. If the leading exponent is `emin - p` (`-1075` or `-150`), use the sign of the low limb. A positive perturbation rounds to `q`, and zero or a negative perturbation rounds to zero. This comparison preserves even the smallest nonzero perturbation and avoids letting polynomial error decide an exact tie.
4. Account for approximation error at other half-integer boundaries. Bound the difference between the stored polynomial and `2^r` over the full reduced interval, including the extension from trailing limbs at reduction endpoints. One way to do this is to subtract a certified Taylor enclosure from the stored polynomial and bound the resulting polynomial on subintervals with outward rounding. Propagate operation-rounding bounds through the actual Horner steps and three squarings. Include argument error from the base conversion and reduction using a derivative bound for `2^r`. Scale the resulting error by the same power of two as the limbs and include any error in the rounding-cell comparison. Use the fast result only when the resulting interval lies entirely in one rounding cell. Sampled worst-case errors can guide the bound, but cannot certify it.
5. Use a cold higher-precision path when the interval reaches a midpoint. Retain the original input limbs and operation so this path evaluates `exp2`, `exp`, or `10^x` from the original argument. Construct the input exactly or enclose the sum of its limbs with directed rounding. The three operations are increasing, so an inexact input sum requires evaluating the lower input with downward rounding and the upper input with upward rounding. If the input sum is exact, use one downward evaluation and its next representable MPFR value to bracket an inexact result. Reuse the converted limbs and the destination for the two endpoints, and defer compilation of the MPFR path until the first ambiguous result. Convert both bounds to lattice units and increase precision until they give the same nearest-even integer. If MPFR is needed, verify that the required entry points are available on the supported Julia versions and confine their use to the fallback with explicit destination precision and rounding. Avoid changing global BigFloat state inside public functions. Check the fallback's termination contract. In this band the only exact dyadic midpoint for a finite binary input to `exp2` is the zero midpoint handled above. For `exp`, a nonzero binary input has a transcendental exponential. For `10^x` and negative binary inputs, an integral exponent leaves factors of 5 in the denominator and a nonintegral exponent gives an irrational result. Keep the fallback off the normal path and measure how often it runs. If the fast bound is unavailable at first, use the directed path for the low band during verification and establish the bound before accepting the performance change.

### Dispatch and source placement

Keep the native reconstruction and its helpers beside the exponential kernel in [explog.jl](../src/math/elementary/explog.jl). Use concrete float types and compile-time operation selection so the ordinary path does not allocate or dispatch dynamically. Keep any high-precision fallback out of line.

In [templated.jl](../src/math/elementary/templated.jl), public `exp(::Double32)` currently promotes to `Double64`. A Double64 reconstruction alone cannot fix subsequent rounding at the Float32 boundary. Specialize only this wrapper if needed. Preserve promotion for ordinary inputs and route the Float32 low band through the shared lattice reconstruction. Use a conservative dispatch bound whose proof includes both input limbs and whose upper end stays below the end of the first normal Float32 binade, or choose the path using the converted base-2 head in the target precision. Leave the public logarithm promotion and the Double16 and nested-precision wrappers in place.

## 6. Recover cancellation-heavy FMA throughput

In [fma.jl](../src/math/arithmetic/fma.jl), the current ten-slot expansion is allocation-free. A repeated A/B/A comparison on Julia 1.13.3 measured about 108 ns per cancelling result with the old vector implementation and 129 ns with the current tuple implementation. The old implementation allocated 288 bytes per call. Treat these as workload-specific observations. Keep the ordinary FMA path and the cancellation threshold as they are.

1. Inspect the optimized code for `_fma_refined` and `_fma_grow_expansion` with runtime operands. Look for tuple copies from dynamic `Base.setindex`, bounds-check branches inside the append path, and code growth from repeated inlining. Check the emitted code before attributing the entire latency difference to tuple copying.
2. Prototype an allocation-free grow loop with statically addressable slots. Use the insertion sequence to bound the live length at each stage, and test whether specialization on those bounds gives the compiler constant slot indices without duplicating expensive code. A compact in-place buffer is a second candidate if the compiler proves it does not escape on the oldest supported Julia version. Before attempting in-place compaction, establish the invariant that the write index is at most the number of source terms already consumed. Read each term before writing its residual, and append the last carry after consuming the input.
3. Keep one private expansion implementation near `_fma_refined`. Derive storage capacity and initialization from the same ten-term bound of two components per product and two addend limbs. Preserve the insertion order, the existing error-free transforms and zero elimination, and the final low-to-high accumulation. Avoid replacing the expansion with a shorter arithmetic expression that can discard terms during cancellation.
4. In [test/fma.jl](../test/fma.jl), retain the exact-cancellation allocation test and add warmed, runtime-argument checks for `fma` and `muladd` with nonzero product and addend low limbs and a nonzero cancelling residual. Assert inference, zero allocations and agreement with an independently computed high-precision result. During development, compare both result limbs against `404f1215` for seeded cancellation cases including exact zero, several residual depths and signs, wide exponent gaps, and near-threshold cases. Use sufficient reference precision for the test exponents.
5. Benchmark a warmed preallocated-output loop with varying nonzero low limbs, using `z = -(x*y)` for a cancellation-heavy batch. Also measure ordinary inputs, mixed batches and a batch long enough to include allocation and GC costs on the old implementation. Alternate each candidate with `404f1215` and the old vector implementation on the same machine. Require zero allocations and unchanged ordinary throughput within noise. Aim to eliminate the reproduced cancellation penalty. Accept a candidate only if the improvement survives repeated runs and the supported-version checks. Retain the allocation-free implementation if the tuning fails those checks and report the remaining latency tradeoff.

## 7. Preserve double-word cube-root accuracy at extreme magnitudes

In [op_dd_dd.jl](../src/math/ops/op_dd_dd.jl), `cbrt_dd_dd` can overflow or underflow intermediates even though the cube root is representable. Its fallback computes a scalar cube root from the high limb and loses the input's low-limb contribution. Preserve the tuple return from that kernel and the `DoubleFloat{T}` construction in [op_db_db.jl](../src/math/ops/op_db_db.jl).

1. Separate the existing Newton body from range handling. Keep the direct path for ordinary finite `Double64` inputs. Use a conservative magnitude window such as `[2^-256, 2^256]` for the absolute high limb as a starting point. Verify headroom for the input square, reciprocal, seed square and cube, and corrected products at both endpoints before adopting the window. Dispatch using magnitude comparisons so the ordinary path does not need an exponent decomposition. Keep the normalization path out of line if doing so improves ordinary throughput.
2. For an extreme finite nonzero normalized input, compute `e = exponent(abs(hi))` and `k = fld(e, 3)`. Scale each limb by `2^(-3k)`, evaluate the same Newton body on the scaled pair, and scale each output limb by `2^k`. The scaled high limb has absolute value in `[1, 8)`, with sign preserved. Floor division is necessary for negative exponents. Use scalar exponent-aware scaling on the limbs so the scale factor itself never needs to be materialized. In particular, normalizing the smallest Float64 subnormal requires an upward shift of 1074. Verify that any input low limb lost during downscaling lies below working precision and that a material low limb survives. Validate the scaled output as a normalized pair.
3. Handle zero, NaN, and infinities before exponent decomposition, preserving existing public behavior and the sign of zero where it is already preserved. Check the normal public dispatch through [arith.jl](../src/math/ops/arith.jl) and the Double16 and Double32 promotion in [templated.jl](../src/math/elementary/templated.jl). Keep the window and proof specific to the native Float64 implementation unless extending the kernel to other limb types is independently justified. Once finite supported inputs are protected by the range guard, remove the silent scalar fallback for those inputs and document which magnitudes need rescaling.
4. Extend [test/concrete_accuracy.jl](../test/concrete_accuracy.jl) with signed versions of `Double64(2.0^600, 2.0^545)` and `Double64(0x1p-1020, nextfloat(0.0))`, the smallest positive subnormal, heads near the normal/subnormal and range-dispatch boundaries, and values near `floatmax(Double64)`. Include exact powers of eight and adjacent exponents to exercise all three scale remainders, with low limbs of both signs where representable. Compare both limbs together against a high-precision reference using a working-precision tolerance comparable to ordinary cube-root results. An assertion on the high limb alone can miss the reported failure. Check type, special values, and ordinary behavior separately. Avoid using `r^3` in the target precision as the oracle at extreme magnitudes.
5. Benchmark preallocated arrays with ordinary, extreme, and mixed exponents. Require zero allocations, working-precision accuracy on the extreme fixtures, and no repeatable ordinary-path regression. A local prototype using the existing body after scaling reduced the large reproducer's relative error from about `9.25e-18` to `1.11e-33` and the tiny two-limb reproducer's error from `1.85e-17` to `2.40e-33`. Use those cases as checks on the implementation, then sweep a broader exponent range.

### Measurement protocol

1. Use the same Julia executable, resolved dependencies where compatible, optimization settings, thread count, and machine for each paired run. Record the CPU, Julia version, commit or patch identifier, input seed and counts. Repeat on Julia 1.10 and a current supported version. Run any incompatible historical environment separately and identify the difference.
2. Generate and validate operands outside the timed region. Use runtime, type-stable inputs, preallocate outputs for array loops, and consume results so the compiler retains the work. Warm each operation and argument type before measuring. Time a dependent scalar sequence for latency and a loop over independent inputs for throughput. Verify that any dependent sequence stays within the intended numerical path.
3. Alternate baseline and candidate in paired rounds with the same inputs and mix order. Include clustered and deterministically shuffled mixtures, and record their actual path counts. Measure elapsed time per element and bytes and allocations per call. Report median paired deltas and run-to-run spread, with absolute and percentage changes. For the fallback, report upper-tail batch timings with batch size and rate, plus per-fixture latency when batching would hide a rare expensive input. Keep diagnostic counters out of production timings.
4. Measure cold compilation separately in fresh Julia processes for changes that alter specialization, inlining or fallback code. Inspect generated code for new hot-path calls, lost vectorization or substantial code growth if timings regress. Measure allocations after warm-up so compilation and fixture construction do not affect the result.
5. Use the paired baseline's spread to distinguish noise from a repeatable hit. Flag every repeatable slowdown in the results, even where correctness justifies it. Record each workload independently so a faster path cannot hide a slower one. Investigate ordinary-path slowdowns and unexpected allocations before accepting a change. For a correctness fix with an unavoidable cold-path cost, record the affected range or fallback rate and give the measured tradeoff. The FMA tuning needs a repeatable refined-path gain with zero allocations and ordinary throughput within noise.

For each result record the operation and type, input regime, baseline and candidate revisions, median time per result, paired timing delta and spread, allocation delta, and correctness status. For mixed workloads also record the mixture and observed path rates. Leave metrics for unimplemented candidates pending.
